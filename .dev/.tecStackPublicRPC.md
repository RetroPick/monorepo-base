## 1. Philosophy and Design Constraints

### 1.1 Core Engineering Philosophy

This is a **lean, boring-stack, production-first architecture**. The prediction market protocol
is complex enough at the smart contract layer — the infrastructure must be simple, observable,
and recoverable without heroics.

Guiding principles, in priority order:

1. **Correctness over cleverness.** A keeper that misses an epoch is worse than an ugly Go function.
2. **PostgreSQL for everything.** One database. No Redis, no Kafka, no Elasticsearch unless
   PostgreSQL genuinely cannot do the job. It can. LISTEN/NOTIFY replaces most message queues
   at this scale. `SKIP LOCKED` queues replace job runners.
3. **Single VPS until it cracks.** A single well-tuned VPS with PostgreSQL on a Unix socket
   is faster than an RDS instance behind a NAT gateway. Add the second server when the first
   one runs out of CPU, not because someone said "microservices".
4. **Go for the backend.** Statically compiled, single binary per service, trivial to deploy,
   goroutine concurrency maps directly to the event-driven workload.
5. **Every state change is auditable.** The prediction market runs real money. Every operator
   action, every keeper call, every oracle read, every epoch transition must produce a
   durable log row in PostgreSQL before the on-chain transaction is broadcast.
6. **Fail loudly, recover explicitly.** The runbook from the smart contract Operator Runbook
   applies equally to this layer. Pause first, inspect, then recover. No silent retries.

### 1.2 What the Stack Must Support

Derived from the smart contract documentation:

**Chain-facing requirements:**
- Index all MarketEngine events in real time (EpochOpened, EpochLocked, EpochResolved,
  RollingHalted, YieldRouterDisabled, etc.)
- Execute keeper calls: `executeRollingRound`, `lockEpoch`, `resolveEpoch`, with precise
  timing windows and buffer enforcement
- Monitor Chainlink oracle feed freshness per template before every keeper call
- Support TrustedReporter signature generation and posting
- Support emergency pause, recovery, and reconciliation flows

**User-facing requirements:**
- Wallet-connected deposits, switches, claims
- Real-time market state (pool sizes, current price, time to lock/resolve)
- Historical epoch results and personal position history
- WebSocket feed for live price ticks and pool updates
- Position view: getUserEpochs pagination, per-epoch claim status

**Operator-facing requirements:**
- Full protocol state dashboard: globalPaused, yieldRouterDisabled, activeEpochIds,
  unreconciledRecoveredAmount per template
- Template management: upsert, initialize, configure
- Keeper health: last execution, next window, halt reason
- Alert management and incident tracking
- Fee withdrawal interface

### 2.1 Service Inventory

| Service | Binary | Port | Purpose |
|---------|--------|------|---------|
| `retropick-api` | Go | 8080 | REST + WebSocket API for user and operator frontends |
| `retropick-index` | Go | 8081 (internal) | Block-by-block event indexer from Base L2 |
| `retropick-keeper` | Go | 8082 (internal) | Scheduled epoch lifecycle automation |
| `retropick-oracle` | Go | 8083 (internal) | Chainlink feed freshness monitor |
| `retropick-reporter` | Go | 8084 (internal) | TrustedReporter EIP-712 signer |
| `retropick-alert` | Go | 8085 (internal) | Notification dispatcher (PagerDuty/Telegram/email) |
| `nginx` | system | 80/443 | Reverse proxy, TLS termination |
| `postgresql` | system | 5432 (Unix socket) | Primary database |
| `app-frontend` | Node | 3000 | User-facing Next.js |
| `ops-frontend` | Node | 3001 | Operator dashboard Next.js |

All Go services run as `systemd` units. PostgreSQL listens on Unix socket only — no TCP exposure.

## 3. VPS Hardware and OS Layer

### 3.1 Server Specification

**Provider:** Hetzner Cloud (cheapest reliable provider with European data center)  
**Initial tier:** CX32 (4 vCPU, 8 GB RAM, 80 GB NVMe) — ~€11/month  
**Scale tier:** CX52 (8 vCPU, 32 GB RAM, 240 GB NVMe) — ~€38/month

**Why Hetzner over DigitalOcean or Linode:** 4× cheaper per core, better NVMe I/O,
same network quality. Base L2 RPC calls are outbound-only so datacenter location matters
minimally.

**Additional volume:** 200 GB detached block storage for PostgreSQL WAL archive — ~€9.20/month  
**Snapshot:** weekly automated VPS snapshot — ~€2/month  
**Total infrastructure cost:** ~€55/month at production scale

## 4. PostgreSQL Schema — Single Database for Everything

### 4.1 Database Layout

```sql
-- Three logical databases, all on the same PostgreSQL instance
-- connected via Unix socket for zero-latency access

CREATE DATABASE retropick_main;   -- market state, positions, epochs
CREATE DATABASE retropick_ops;    -- operator actions, keeper logs, incidents
CREATE DATABASE retropick_audit;  -- immutable append-only audit trail
```

### 4.2 PostgreSQL Configuration (`postgresql.conf`)

```ini
# Performance tuning for 8GB RAM VPS
shared_buffers = 2GB                    # 25% of RAM
effective_cache_size = 6GB             # 75% of RAM
work_mem = 16MB                        # per sort/hash operation
maintenance_work_mem = 512MB           # for VACUUM, index builds
max_connections = 200                  # Go services use pgx pool
min_wal_size = 512MB
max_wal_size = 4GB
wal_level = replica                    # required for WAL archiving
archive_mode = on
archive_command = 'cp %p /mnt/wal-archive/%f'
checkpoint_completion_target = 0.9
random_page_cost = 1.1                 # NVMe SSD — sequential ≈ random
effective_io_concurrency = 200        # NVMe parallelism
default_statistics_target = 100
wal_buffers = 64MB
synchronous_commit = on               # correctness over speed for financial data
fsync = on                            # never disable on a financial system

# Connection pooling via PgBouncer (transaction mode)
# Go services connect to PgBouncer on Unix socket
# PgBouncer connects to PostgreSQL on Unix socket

# LISTEN/NOTIFY for internal pub/sub
# Used by indexer → api-server for real-time updates
```

### 4.5 Schema — `retropick_ops`

```sql
-- ─────────────────────────────────────────────────────────────────────────
-- KEEPER EXECUTION LOG
-- ─────────────────────────────────────────────────────────────────────────

CREATE TYPE keeper_action AS ENUM (
  'genesis_start_rolling', 'genesis_lock_rolling', 'execute_rolling_round',
  'open_epoch', 'lock_epoch', 'resolve_epoch', 'cancel_epoch',
  'halt_rolling_market', 'cancel_rolling_epoch_while_halted',
  'reset_rolling_lifecycle', 'pause_program', 'unpause_program',
  'yield_emergency_withdraw', 'reconcile_routed_principal',
  'withdraw_fees', 'reset_oracle_cursor', 'set_yield_router',
  'upsert_template', 'initialize_market'
);

CREATE TYPE keeper_result AS ENUM ('success', 'failed', 'reverted', 'skipped');

CREATE TABLE keeper_executions (
  id             BIGSERIAL PRIMARY KEY,
  action         keeper_action NOT NULL,
  template_id    BYTEA,
  epoch_id       BIGINT,
  result         keeper_result NOT NULL,
  tx_hash        VARCHAR(66),
  block_number   BIGINT,
  gas_used       BIGINT,
  gas_price_gwei NUMERIC(20, 9),
  error_message  TEXT,
  pre_state      JSONB,   -- snapshot of relevant state before execution
  post_state     JSONB,   -- snapshot after execution
  executed_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  executed_by    VARCHAR(42) NOT NULL   -- sender address
);

CREATE INDEX idx_keeper_executions_template ON keeper_executions(template_id, executed_at DESC);
CREATE INDEX idx_keeper_executions_result ON keeper_executions(result) WHERE result != 'success';

-- ─────────────────────────────────────────────────────────────────────────
-- KEEPER SCHEDULE (what the keeper intends to do and when)
-- ─────────────────────────────────────────────────────────────────────────

CREATE TYPE schedule_status AS ENUM ('pending', 'executing', 'done', 'failed', 'cancelled');

CREATE TABLE keeper_schedule (
  id              BIGSERIAL PRIMARY KEY,
  template_id     BYTEA NOT NULL,
  epoch_id        BIGINT,
  action          keeper_action NOT NULL,
  scheduled_at    TIMESTAMPTZ NOT NULL,
  window_end_at   TIMESTAMPTZ NOT NULL,   -- buffer deadline
  status          schedule_status NOT NULL DEFAULT 'pending',
  execution_id    BIGINT REFERENCES keeper_executions(id),
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- SKIP LOCKED pattern: keeper SELECT FOR UPDATE SKIP LOCKED
-- picks next pending job atomically without a separate queue service
CREATE INDEX idx_keeper_schedule_pending ON keeper_schedule(scheduled_at)
  WHERE status = 'pending';

-- ─────────────────────────────────────────────────────────────────────────
-- ORACLE HEALTH TRACKING
-- ─────────────────────────────────────────────────────────────────────────
```

## 6. Event-Driven Pipeline — Chain Indexer

### 6.1 Architecture

The indexer is a separate Go binary (`retropick-index`) that subscribes to Base L2
event logs, decodes them, writes to PostgreSQL, and emits NOTIFY signals to the
API server.

```
Base L2 Node (Alchemy)
        │
        │ eth_getLogs (poll every 2s)
        │ + eth_subscribe newHeads (WebSocket)
        ▼
┌──────────────────────────────────────────────────────────────────────┐
│                    retropick-index (Go)                               │
│                                                                       │
│  ┌─────────────────┐   ┌─────────────────┐   ┌──────────────────┐   │
│  │  Block Fetcher  │──▶│  Event Decoder  │──▶│  State Updater   │   │
│  │  (RPC poller)   │   │  (ABI decode)   │   │  (PG writer)     │   │
│  └─────────────────┘   └─────────────────┘   └────────┬─────────┘   │
│                                                        │              │
│  ┌─────────────────────────────────────────────────────▼──────────┐  │
│  │  Reorg Handler — detects chain reorgs, rolls back PG state     │  │
│  │  (keep 64-block buffer, compare block hashes)                  │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                        │              │
│                               pg_notify('market_update', payload)     │
│                               pg_notify('keeper_alert', payload)      │
└──────────────────────────────────────────────────────────────────────┘
        │
        ▼
PostgreSQL (chain_events, epochs, positions, ledgers)
        │
        │ NOTIFY
        ▼
retropick-api (WebSocket hub fan-out)
```

### 6.2 Events Indexed (from MarketEngine)

| Event | Action |
|-------|--------|
| `EpochOpened(templateId, epochId, openAt, lockAt, resolveAt)` | INSERT epoch row, UPDATE ledger.activeEpochId, schedule keeper lock action |
| `EpochLocked(templateId, epochId)` / `EpochLockedV2(...)` | UPDATE epoch status→locked, write checkpointA, schedule keeper resolve action |
| `EpochResolved(templateId, epochId)` / `EpochResolvedV2(...)` | UPDATE epoch status→resolved, write checkpointB + settlement outputs, set claimable=true |
| `EpochCancelled(templateId, epochId, reason, voided)` | UPDATE epoch status→cancelled/voided, set refundMode |
| `PositionDeposited(templateId, epochId, user, outcomeIdx, amount)` | UPSERT position, UPDATE epoch outcome_pools, notify pool_update |
| `PositionSwitched(...)` | UPDATE position stakes, UPDATE epoch pools |
| `Claimed(templateId, epochId, user, amount)` | UPDATE position.claimed=true, UPDATE epoch.claimed_total |
| `RollingRoundExecuted(templateId, prev, cur, next)` | Cascade UPDATE for prev→resolved, cur→locked, next→open |
| `RollingHalted(templateId, reason, atEpoch)` | UPDATE ledger rolling_phase→halted, notify keeper_alert |
| `YieldRouterDisabled(templateId)` | UPDATE global state, notify keeper_alert CRITICAL |
| `YieldEmergencyWithdrawn(templateId, amount)` | UPDATE ledger unreconciled_recovered, open incident |
| `OracleCursorReset(templateId, feedId)` | Audit log INSERT, notify ops |
| `ModuleRegistered/Revoked/SelectorSet` | Audit log INSERT, notify ops CRITICAL |
| `FeesWithdrawn(templateId, amount)` | UPDATE ledger.fee_reserve_total |

### 6.3 Reorg Safety

```go
// Indexer maintains a 64-block rolling buffer of block hashes.
// On each new block:
// 1. Check if parent hash matches the last indexed block hash.
// 2. If mismatch: reorg detected.
//    a. Walk back to the common ancestor (max 64 blocks).
//    b. DELETE chain_events with block_number > ancestor.
//    c. Re-apply events from the fork block.
//    d. UPDATE indexer_state.reorg_depth.
// 3. If reorg depth > 20 blocks: CRITICAL alert, pause indexer, human review.

// For financial correctness: all epoch state writes in a single PG transaction
// per block. If PG write fails, the block is retried up to 3 times before alert.
```

## 7. Keeper Automation Service

### 7.1 Keeper Architecture

The keeper (`retropick-keeper`) is the most safety-critical service. It executes
on-chain transactions. Every execution is pre-validated, logged before broadcast,
and post-validated.

```
┌──────────────────────────────────────────────────────────────────────┐
│                     retropick-keeper (Go)                             │
│                                                                       │
│  ┌─────────────────┐                                                  │
│  │  Schedule Poller│  SELECT * FROM keeper_schedule                   │
│  │  (5-second tick)│  WHERE status='pending'                          │
│  │                 │  AND scheduled_at <= NOW()                       │
│  │                 │  FOR UPDATE SKIP LOCKED                          │
│  │                 │  LIMIT 1                                         │
│  └────────┬────────┘                                                  │
│           │                                                           │
│  ┌────────▼────────┐                                                  │
│  │ Pre-flight Check│  For each action:                                │
│  │                 │  1. Read live contract state (chain call)        │
│  │                 │  2. Verify action is still valid                 │
│  │                 │  3. Check oracle freshness                       │
│  │                 │  4. Check buffer window still open               │
│  │                 │  5. Check protocol not paused                    │
│  └────────┬────────┘                                                  │
│           │ passes                                                    │
│  ┌────────▼────────┐                                                  │
│  │  Transaction    │  1. INSERT keeper_executions (pre_state, pending)│
│  │  Builder        │  2. Estimate gas + sanity check                  │
│  │                 │  3. Sign transaction (keeper private key)        │
│  │                 │  4. Broadcast to Base L2                        │
│  │                 │  5. Wait for receipt (timeout: 60s)              │
│  │                 │  6. UPDATE keeper_executions (result, tx_hash)   │
│  │                 │  7. Verify post-state via chain read             │
│  └────────┬────────┘                                                  │
│           │                                                           │
│  ┌────────▼────────┐                                                  │
│  │  Post-Exec      │  On success: schedule next action for template   │
│  │  Handler        │  On failure: classify error, alert, open incident│
│  └─────────────────┘                                                  │
└──────────────────────────────────────────────────────────────────────┘
```

### 7.2 Keeper Pre-flight Checks (Per Action Type)

```go
// executeRollingRound pre-flight:
type RollingRoundPreflight struct {
    rollingPhase     string        // must be "live"
    globalPaused     bool          // must be false
    resolveWindow    TimeWindow    // now >= prev.resolveAt
    lockWindow       TimeWindow    // now >= cur.lockAt
    resolveBuffer    time.Duration // now <= prev.resolveAt + bufferSeconds
    lockBuffer       time.Duration // now <= cur.lockAt + bufferSeconds
    oracleFresh      bool          // feed updatedAt within maxDelaySeconds
    routerHealthy    bool          // !yieldRouterDisabled
    noUnreconciledRecovery bool    // totalUnreconciledRecovered == 0
    bufferPressure   float64       // percentage of buffer remaining (alert if < 25%)
}

// Fail-safe: if any preflight fails, the action is:
// 1. Marked as 'skipped' in keeper_schedule
// 2. An alert is emitted if buffer pressure is < 25% remaining
// 3. An incident is opened if buffer is expired (miss is imminent)
// Never retried blindly. Operator must intervene.
```

### 7.3 Keeper Schedule Builder

```go
// After EpochOpened event:
// INSERT INTO keeper_schedule:
//   action=lock_epoch, scheduled_at=lockAt, window_end_at=lockAt+bufferSeconds

// After EpochLocked event:
// INSERT INTO keeper_schedule:
//   action=resolve_epoch, scheduled_at=resolveAt, window_end_at=resolveAt+bufferSeconds

// After RollingRoundExecuted event:
// The next round's resolve and lock windows are derived from the new epoch's timings
// INSERT INTO keeper_schedule:
//   action=execute_rolling_round, scheduled_at=new_lockAt, window_end_at=new_lockAt+bufferSeconds

// Buffer pressure alerting:
// Poll keeper_schedule every 60 seconds
// For any pending action: if (window_end_at - NOW()) < 0.25 * bufferSeconds → WARN alert
// For any pending action: if (window_end_at - NOW()) < 0     → CRITICAL alert + incident
```

### 7.4 Gas Price Strategy

```go
// Base L2 (OP Stack): EIP-1559 base fee + priority fee
// Strategy: use eth_gasPrice or eth_feeHistory for base fee estimate
// Priority fee: 0.001 gwei (Base L2 is very cheap)
// Gas multiplier: 1.2x estimated gas as limit
// Resubmit if not mined within 30s: bump priority fee by 50%
// Max resubmit attempts: 3
// If still not mined after 3 attempts: alert + mark as failed
// Never use high gas price automatically — require operator approval above threshold

type GasConfig struct {
    MaxBaseFeeGwei    float64  // hard cap — default 0.1 gwei on Base L2
    PriorityFeeGwei   float64  // default 0.001 gwei
    GasLimitMultiplier float64 // default 1.2x estimate
    ResubmitAfterSec  int      // default 30s
    MaxResubmitCount  int      // default 3
}
```

## 9. TrustedReporter Service

### 9.1 Architecture

```go
// retropick-reporter: signs and posts TrustedReporter oracle data
// Used for: Corridor markets (OHLC), Cascade markets (OHLC),
//           and any Threshold market configured with TrustedReporter oracle kind

// Security model: private key stored in env var, NEVER in PostgreSQL

// Posting flow for a market resolution:
// 1. Fetch raw data from approved source (NOAA API, internal OHLC computation)
// 2. Validate data: range checks, source health checks
// 3. Compute EIP-712 typed data hash (matching TrustedReporterAdapter's domain)
// 4. Sign with private key
// 5. INSERT into audit_log (payload includes message hash, signer, data)
// 6. Call postResolveResult() or postOhlcResult() on TrustedReporterAdapter
// 7. Wait for on-chain confirmation

// - Reporter key is separate from keeper key
// - Reporter key has ZERO on-chain admin access
// - Rotate reporter key via setTrustedReporter (operator flow, not automated)
// - Alert immediately if reporter key signs anything outside normal schedule
```

## 16. Backup, Recovery, and WAL Archiving

### 16.1 Backup Strategy

```bash
# Continuous WAL archiving to attached volume
# postgresql.conf: archive_command = 'cp %p /mnt/wal-archive/%f'
# This gives point-in-time recovery (PITR) to any point in the last 7 days

# Daily base backup with pg_basebackup
# /opt/retropick/scripts/backup.sh
#!/bin/bash
set -euo pipefail

BACKUP_DIR=/mnt/wal-archive/base_backups
DATE=$(date +%Y%m%d_%H%M%S)

pg_basebackup \
  --pgdata="${BACKUP_DIR}/${DATE}" \
  --format=tar \
  --compress=9 \
  --checkpoint=fast \
  --progress

# Keep last 7 daily backups
find ${BACKUP_DIR} -maxdepth 1 -type d -mtime +7 -exec rm -rf {} +

# Upload to off-site (Cloudflare R2 or Hetzner Object Storage)
rclone sync ${BACKUP_DIR}/${DATE} r2:retropick-backups/${DATE}

echo "Backup completed: ${DATE}"
```

### 16.2 Recovery Time Objective (RTO)

| Scenario | RTO | Procedure |
|----------|-----|-----------|
| PostgreSQL crash (data intact) | < 1 minute | `systemctl restart postgresql` |
| Corrupt data file | < 30 minutes | PITR from WAL archive |
| VPS total loss | < 2 hours | New VPS + restore base backup + replay WAL |
| Catastrophic loss (all backups) | N/A — use chain as source of truth | Rebuild from chain events |

**Note on chain as ultimate truth:** The smart contract state is the canonical source.
If the PostgreSQL database is completely lost, the indexer can replay all events
from genesis block and rebuild the full state. This is the ultimate recovery path.
Estimated replay time from genesis: ~4 hours for 1 year of events.

## 20. Incident Response Runbooks

### 20.1 RollingHalted Response

```
TRIGGER: RollingHalted event indexed / keeper_alert NOTIFY received
SEVERITY: HIGH

1. READ OPERATOR STATE
   curl -H "Authorization: Bearer ${OPS_TOKEN}" \
     https://ops.retropick.xyz/api/v1/ops/templates/{templateId}/state
   
   Capture: rollingHaltReason, haltedAtEpochId, activeEpochId

2. CLASSIFY HALT REASON
   - BufferMissOnLock / BufferMissOnResolve:
     * Was the keeper running? Check keeper logs
     * Was the oracle fresh at the time? Check oracle_health table
     * Was it a transient RPC issue?
   
   - OracleFailure:
     * Is the feed still stale now? Check oracle_health.is_stale
     * Is it a confidence issue? Check oracle_readings.confidence_e8
   
   - ManualAdmin: intentional halt, skip to step 5

3. IF ORACLE IS STILL STALE: WAIT
   Do not attempt recovery while the oracle is stale.
   Open incident. Monitor oracle health.
   Alert when oracle recovers.

4. IF ROOT CAUSE RESOLVED: PREPARE RECOVERY
   Via admin Safe (multisig):
   a. pauseProgram(true)
   b. cancelRollingEpochWhileHalted(templateId, haltedEpochId, reason, false)
   c. resetRollingLifecycle(templateId, nextEpochId)
   d. pauseProgram(false)
   
   Verify via: getOperatorTemplateView(templateId)
   Expected: rollingPhase=uninitialized, no stuck epochs

5. RESTART ROLLING
   Keeper will execute genesisStartRolling within 30 seconds of unpause.
   Monitor: watch keeper_schedule table and keeper_executions.

6. CONFIRM RECOVERY
   After 2 successful executeRollingRound calls: mark incident resolved.
```

### 20.2 YieldRouterDisabled Response

```
TRIGGER: YieldRouterDisabled event indexed
SEVERITY: CRITICAL — page immediately

This means 3 consecutive withdrawScaled failures occurred.
User deposits are no longer routing to Aave.
```

## The Problem: Where RPC Calls Are Wasted

Original design had 4 sources of unnecessary RPC calls:

1. **Keeper pre-flight polling every 5s** — calls `eth_call` even when no action is due
2. **Oracle monitor polling every 60s** — separate `latestRoundData()` per feed
3. **API chain reader** — re-reads live state from chain that the indexer already has in PG
4. **Duplicate block fetching** — indexer fetches blocks AND logs separately

The fix: **PostgreSQL is the truth for everything the indexer has already seen.
RPC is used only for (a) indexing new events and (b) broadcasting transactions.**

## Revised Service Designs

### 1. Indexer — Single Source of Chain Truth

The indexer is the ONLY service that polls the chain.
Everything else reads from PostgreSQL.

```
OLD (wastes RPC):
  eth_subscribe newHeads → eth_getLogs per block → eth_getBlockByNumber

NEW (minimal RPC):
  Poll eth_getLogs with fromBlock/toBlock range every 40 seconds
  Single call fetches all MarketEngine events + Chainlink AnswerUpdated events
  in one batch per poll cycle.
```

```go
// Indexer poll loop — single eth_getLogs call per tick

const POLL_INTERVAL = 40 * time.Second   // 40s >> Base L2 ~2s block time
                                          // Fetches ~20 blocks per call
                                          // = 2,160 getLogs calls/day

func (idx *Indexer) pollLoop(ctx context.Context) {
    ticker := time.NewTicker(POLL_INTERVAL)
    for {
        select {
        case <-ticker.C:
            idx.fetchBatch(ctx)
        case <-ctx.Done():
            return
        }
    }
}

func (idx *Indexer) fetchBatch(ctx context.Context) {
    // Read last indexed block from PG — no extra RPC call
    var fromBlock uint64
    row := idx.db.QueryRow(ctx, "SELECT last_block FROM indexer_state WHERE id=1")
    row.Scan(&fromBlock)
    fromBlock++ // start from next unindexed block

    // Get current block number — 1 eth_blockNumber call
    latest, _ := idx.rpc.BlockNumber(ctx)
    if latest <= fromBlock { return } // nothing new

    toBlock := min(latest, fromBlock+100) // batch max 100 blocks

    // ONE eth_getLogs call fetches ALL events we care about
    // Both MarketEngine events AND Chainlink AnswerUpdated in one shot
    logs, _ := idx.rpc.FilterLogs(ctx, ethereum.FilterQuery{
        FromBlock: big.NewInt(int64(fromBlock)),
        ToBlock:   big.NewInt(int64(toBlock)),
        Addresses: []common.Address{
            idx.marketEngineAddr,
            // Chainlink feed proxy addresses — so we index price updates too
            // This means oracle monitor reads from PG, not from chain
            idx.btcUsdFeed,
            idx.ethUsdFeed,
            idx.stakingAprFeed,
            // ... all registered feed addresses
        },
    })

    // Decode + write to PG in one transaction
    idx.processBatch(ctx, logs, fromBlock, toBlock)
}
```

**Why 40 seconds and not 2 seconds:**
- Base L2 blocks are ~2s but we don't need per-block latency
- For prediction markets: lock/resolve windows are measured in minutes or hours
- 40s polling means max 40s delay on event indexing — perfectly acceptable
- If a specific event is time-critical (keeper execution), keeper reads
  directly from chain one time (not in a loop) — see section 3 below

**Chainlink feed events indexed via the same getLogs call:**

### 2. Oracle Monitor — Eliminated as Separate Service

The oracle monitor is now a **PostgreSQL-backed alerter**, not an RPC poller.

```go
// retropick-oracle service replaced by oracle_alerter.go inside retropick-alert

// Runs every 60 seconds, reads oracle_health from PG (not from chain)
func (a *Alerter) checkOracleHealth(ctx context.Context) {
    rows, _ := a.db.Query(ctx, `
        SELECT
            feed_id,
            label,
            last_updated,
            heartbeat_sec,
            EXTRACT(EPOCH FROM (NOW() - last_updated)) AS staleness_sec,
            is_stale,
            alert_sent
        FROM oracle_health oh
        JOIN feed_registry fr USING (feed_id)
        WHERE fr.is_active = TRUE
    `)

    for rows.Next() {
        var f OracleHealthRow
        rows.Scan(&f.FeedID, &f.Label, &f.LastUpdated, &f.HeartbeatSec,
                  &f.StalenessSec, &f.IsStale, &f.AlertSent)

        // Alert if staleness > 80% of heartbeat (20% early warning)
        warnThreshold := float64(f.HeartbeatSec) * 0.8
        critThreshold := float64(f.HeartbeatSec)

        if f.StalenessSec > critThreshold && !f.AlertSent {
            a.sendCriticalAlert(ctx, "oracle_stale", f.Label, f.StalenessSec)
            a.db.Exec(ctx, "UPDATE oracle_health SET alert_sent=TRUE, alert_sent_at=NOW() WHERE feed_id=$1", f.FeedID)
        } else if f.StalenessSec > warnThreshold && !f.AlertSent {
            a.sendWarnAlert(ctx, "oracle_staleness_warning", f.Label, f.StalenessSec)
        }
    }
}
// RPC calls: 0. All data comes from PG.
```

**When does oracle_health get updated?**
The indexer updates it every time a Chainlink `AnswerUpdated` event is indexed.
If no `AnswerUpdated` appears for a feed within the heartbeat window,
`staleness_sec` grows and the alert fires automatically.

**Edge case: what if a feed has zero on-chain activity (no trades, no updates)?**
Chainlink feeds emit `AnswerUpdated` on heartbeat even if price unchanged.
So if we index the feed's address, we will always see its heartbeat events.
This is the correct behavior — no special polling needed.

### 3. Keeper — PG-Driven, RPC Only for Actual Execution

```
OLD: Keeper polls eth_call every 5 seconds to check if action is valid
     = 17,280 RPC calls/day doing nothing

NEW: Keeper reads keeper_schedule from PG (already 0-latency on Unix socket)
     RPC is called exactly once: right before broadcasting a transaction
     = 0 idle RPC calls + 1 pre-execution call per actual transaction
```

```go
// Keeper main loop — polls PG every 5s (Unix socket, sub-millisecond)
func (k *Keeper) loop(ctx context.Context) {
    ticker := time.NewTicker(5 * time.Second)
    for range ticker.C {
        k.processNextPending(ctx)
    }
}

func (k *Keeper) processNextPending(ctx context.Context) {
    tx, _ := k.db.Begin(ctx)
    defer tx.Rollback(ctx)

    var job KeeperJob
    err := tx.QueryRow(ctx, `
        SELECT id, template_id, epoch_id, action, scheduled_at, window_end_at
        FROM keeper_schedule
        WHERE status = 'pending'
          AND scheduled_at <= NOW()
        ORDER BY window_end_at ASC
        LIMIT 1
        FOR UPDATE SKIP LOCKED
    `).Scan(&job.ID, &job.TemplateID, &job.EpochID, &job.Action, &job.ScheduledAt, &job.WindowEndAt)

    if err != nil { return } // no pending jobs

    // Mark as executing in PG (prevents duplicate pickup)
    tx.Exec(ctx, "UPDATE keeper_schedule SET status='executing' WHERE id=$1", job.ID)
    tx.Commit(ctx)

    // Pre-flight: read state from PG (not from chain)
    // PG state was just updated by indexer (max 40s lag)
    state, _ := k.readStateFromPG(ctx, job.TemplateID)

    // Validate action is still appropriate given PG state
    if !k.preflightFromPG(state, job) {
        k.markSkipped(ctx, job, "preflight_failed_pg_state")
        return
    }

    // SINGLE RPC call: verify the one field that matters most
    // (only for financial safety — the PG state should match but we verify)
    // For rolling: verify rollingPhase is still 'live' and not paused
    // This is 1 eth_call per actual execution (not per 5s poll tick)
    livePhase, paused := k.readRollingPhaseDirect(ctx, job.TemplateID) // 1 eth_call
    if paused || livePhase != "live" {
        k.markSkipped(ctx, job, "protocol_state_changed")
        return
    }

    // Execute transaction
    k.executeAndWait(ctx, job)
}
```

**The key insight:** the PG state is always within 40 seconds of chain state.
For keeper windows measured in minutes (typically rollingBufferSeconds ≥ 30s,
usually 2-5 minutes), 40s PG lag is completely safe.

**The one remaining eth_call:** one final chain read per execution protects against
the 40s PG lag window. Cost: 1 RPC call per keeper execution, not per 5s poll.
With ~50 executions/day across all templates: 50 RPC calls/day from keeper.

```go
// config.go — public RPC endpoints in priority order

var PublicBaseRPCEndpoints = []string{
    "https://mainnet.base.org",          // Coinbase official — most reliable
    "https://base.llamarpc.com",         // LlamaRPC — no key, generous limits
    "https://1rpc.io/base",              // 1RPC — privacy-focused, no key

    "https://base.rpc.thirdweb.com",     // Thirdweb public

// Retry logic: try each endpoint in order on failure
// If all fail: alert + pause indexer (do not lose events)

type RPCClient struct {
    endpoints []string
    current   int
    mu        sync.Mutex
}

func (c *RPCClient) call(ctx context.Context, method string, params ...interface{}) (json.RawMessage, error) {
    for attempt := 0; attempt < len(c.endpoints); attempt++ {
        endpoint := c.endpoints[c.current % len(c.endpoints)]
        result, err := c.callOne(ctx, endpoint, method, params...)
        if err == nil {
            return result, nil
        }
        c.mu.Lock()
        c.current++
        c.mu.Unlock()
        // log which endpoint failed
    }
    return nil, fmt.Errorf("all RPC endpoints failed")
}
```
