Got it — **probability chart only**. For RetroPick, the probability chart should show how market odds / pool-implied probabilities evolve over time.

It should **not** be the BTC/ETH price chart.

```txt
Probability chart = chance/odds history
Price chart = asset price history
```

# 1. What the probability chart means

For your pool-based market, probability is derived from pool sizes:

```txt
probability(outcome) = outcomePool / totalPool
```

For binary UP/DOWN:

```txt
UP probability   = upPool / totalPool
DOWN probability = downPool / totalPool
```

Example:

```txt
UP pool:   600 USDC
DOWN pool: 400 USDC
Total:   1000 USDC

UP probability   = 60%
DOWN probability = 40%
```

But label it carefully:

```txt
Pool-implied probability
```

not:

```txt
True probability
```

Because it reflects pool composition, not guaranteed real-world probability.

---

# 2. Probability chart data source

The probability chart should come from **market state**, not price feed.

Sources:

```txt
PositionDeposited event
PositionSwitched event
EpochOpened event
EpochLocked event
EpochResolved event
```

Every time pool sizes change, the indexer computes a probability snapshot.

```txt
on PositionDeposited:
  update outcome_pools
  compute probabilities
  insert probability snapshot
  publish WebSocket event

on PositionSwitched:
  update outcome_pools
  compute probabilities
  insert probability snapshot
  publish WebSocket event
```

---

# 3. Probability formula

## Binary market

```txt
upBps = upPool * 10000 / totalPool
downBps = downPool * 10000 / totalPool
```

Use basis points internally:

```txt
10000 = 100%
5600 = 56%
```

Why bps?

```txt
integer safe
no float drift
easy frontend formatting
```

## Multi-outcome market

```txt
probabilityBps[i] = outcomePool[i] * 10000 / totalPool
```

Because of integer division, total may equal 9999 or 10001. That is fine. You can adjust display if needed.

# 4. Empty pool rule

If:

```txt
totalPool == 0
```

Do not show real probability.

Options:

```txt
show “No liquidity yet”
or show neutral visual 50/50 with label “No pool yet”
```

Recommended:

```txt
No liquidity yet
```

Do not chart 50/50 as real data unless an initial virtual liquidity model exists.

# 5. Probability chart table

Add a dedicated table.

```sql
CREATE TABLE probability_snapshots (
  id BIGSERIAL PRIMARY KEY,

  template_id TEXT NOT NULL,
  epoch_id BIGINT NOT NULL,

  source_event_type TEXT NOT NULL,
  source_tx_hash TEXT,
  source_log_index INT,
  block_number BIGINT,
  block_timestamp TIMESTAMPTZ,

  outcome_pools NUMERIC(78,0)[] NOT NULL,
  total_pool NUMERIC(78,0) NOT NULL,

  probability_bps INT[] NOT NULL,

  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

  UNIQUE(template_id, epoch_id, source_tx_hash, source_log_index)
);

CREATE INDEX idx_probability_snapshots_epoch
  ON probability_snapshots(template_id, epoch_id, created_at ASC);

CREATE INDEX idx_probability_snapshots_recent
  ON probability_snapshots(template_id, created_at DESC);
```

Why separate table?

```txt
epochs table = latest state
probability_snapshots = history for chart
```

# 8. WebSocket event

Publish after every pool-changing event.

```json
{
  "seq": 184920,
  "type": "probability_update",
  "channel": "market:btc-15m",
  "scope": "public",
  "templateId": "btc-15m",
  "epochId": 42,
  "blockNumber": 29100221,
  "txHash": "0xabc",
  "createdAt": "2026-05-02T12:03:44Z",
  "payload": {
    "outcomes": ["UP", "DOWN"],
    "probabilityBps": [6100, 3900],
    "outcomePools": ["61000000", "39000000"],
    "totalPool": "100000000"
  }
}
```

You can also avoid a separate `probability_update` and just send `pool_update`.

But for charting, I prefer:

```txt
pool_update = update pool bars
probability_update = append chart point
```

Even if they come from the same indexed event.

# 9. When to create probability snapshots

Create snapshots only when meaningful.

## Must snapshot

```txt
EpochOpened
PositionDeposited
PositionSwitched
EpochLocked
EpochResolved
```

## Optional snapshot

```txt
Claimed
```

Usually not needed because claims do not change market probability after settlement.

## Do not snapshot

```txt
every second
timer ticks
price ticks
oracle ticks
```

Probability only changes when market pool composition changes.

---

# 10. Should probability chart update every second?

No.

Unlike price charts, probability should be **event-driven**.

```txt
User deposits → chart updates
User switches side → chart updates
Epoch locks → chart freezes
Epoch resolves → final marker
```

If nobody trades, probability does not change.

That means it is cheap.

For RetroPick:

```txt
Probability chart frequency = trade event frequency
```

not:

```txt
1 update/sec
```

This is important.

## Open

```txt
chart updates on deposits/switches
```

## Locked


## Resolved

```txt

```

## Cancelled/voided


# 13. Frontend update flow

```txt
1. Load market snapshot
2. Load probability history via REST
3. Subscribe market:{templateId}
4. On probability_update:
   - append point
   - update latest probability display
   - update pool bars if included
5. On epoch_locked:
   - freeze chart
   - draw lock marker
6. On epoch_resolved:
   - draw resolve marker
   - highlight winner
```

# 14. Frontend hook

```ts
type ProbabilityPoint = {
  t: string
  probabilityBps: number[]
  outcomePools: string[]
  totalPool: string
}

export function useProbabilityChart(templateId: string, epochId: number) {
  const queryClient = useQueryClient()

  const history = useQuery({
    queryKey: ['probability-history', templateId, epochId],
    queryFn: () =>
      apiGet(`/api/v1/markets/${templateId}/epochs/${epochId}/probability-history`),
    staleTime: 10_000,
  })

  useRealtimeSubscription(`market:${templateId}`, event => {
    if (event.type !== 'probability_update') return
    if (event.epochId !== epochId) return

    queryClient.setQueryData(
      ['probability-history', templateId, epochId],
      old => appendProbabilityPoint(old, event.payload)
    )
  })

  return history
}
```

# 15. Downsampling rule

If there are too many trade events, downsample for chart display.

For V1, probably unnecessary.

But later:

```txt
If points > 1000:
  group by 5s or 15s buckets
  keep last point per bucket
```

Do not lose final state.

Rule:

```txt
always keep:
- first point
- lock point
- resolve point
- latest point
```

# 18. Probability chart should not use oracle price

Do not calculate probability from BTC price movement.

Wrong:

```txt
BTC is going up → UP probability increases automatically
```

Correct:

```txt
Users put more pool/stake on UP → UP probability increases
```

Price movement may influence users, but it does not directly change market probability unless someone trades.

---

# 19. Probability vs payout

Pool probability and potential payout are related but not identical depending on your fee model.

Show both:

```txt
UP pool-implied probability: 61%
Estimated payout if UP wins: 1.54x
```

Potential payout formula should account for:

```txt
pool sizes
settlement fee
switch fees if relevant
winner distribution math
```

Do not infer payout only from probability if your math differs.

# 20. V1 recommended implementation

For RetroPick V1:

```txt
Chart type:
- binary UP probability line

Data:
- probability_snapshots from indexed pool-changing events

History:
- REST endpoint

Live:
- WebSocket market:{templateId} probability_update

Frequency:
- event-driven only

Storage:
- probability_snapshots table

Frontend:
- update chart only on probability_update
- freeze at lock
- marker at resolve
```

The key rule:

```txt
Probability chart is not a time-price chart.
It is a history of market crowd allocation over the epoch.
```

That is the correct technical design.
